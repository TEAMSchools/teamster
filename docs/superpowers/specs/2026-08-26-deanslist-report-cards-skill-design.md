# DeansList report cards skill — design

Refs #5016

## Context

The progress report cards live in DeansList Report Manager, a hosted browser
editor. There is no version control, no local runtime, and no test harness. You
edit four files in textareas and press Save.

Two properties of that environment shape every decision below:

- **A render either works or silently produces a blank page.** Most failures
  surface as nothing at all — no console error a human will see, no partial
  page.
- **Every change is a copy-paste**, so the local copy and the platform copy
  drift the moment someone forgets which files they touched.

The skill exists to make an agent's edits survivable: reach for a scripted
splice rather than hand-editing, run the gates that catch blank-page causes
before a human pastes anything, and recognise the traps that have each already
cost a real render.

Source material lives in gitignored `.claude/scratch/deanslist/`, distilled from
a build session in August 2026. Every trap named here was observed, not
theorised.

### There are two templates, not three reports

`ES Progress Report` and `HS Progress Report` are the only templates that exist
as-received. MS is a `reportBand` branch **inside** the HS template; ES is
separate and single-band. This matters for the re-paste matrix: an MS-only
change still re-pastes the HS files.

## Scope

### In scope

Report cards only:

- Authoring a new report card from a blank slate
- Editing an existing report card — any of the four files, any band
- Adding or retiring a Handlebars partial
- Writing or changing a GraphQL query against the DeansList schema
- Diagnosing a blank or wrong render
- Knowing what data exists: the GraphQL catalog versus the BigQuery warehouse

### Out of scope

Each exclusion is recorded **in the skill itself**, with its reason, so a future
agent does not absorb it:

- **General reports and dashboard widgets.** A genuinely different runtime. Its
  vendor page is four sections — Overview, Getting Started, Fetching Data,
  "That's It" — with no lifecycle hooks, no four-file anatomy, no partials, and
  no translation. It shares neither the five-stage pipeline nor the file
  anatomy, so it earns its own skill later rather than a branch here.
- **Incident letters and custom forms.** Separate report types. Note that
  `report-manager-docs-report-cards-201.md` is titled "Report Cards/Incident
  Letters 201" but matches "incident" exactly once, in that title — its body is
  entirely report-card-applicable, so the skill may point at it safely.
- **The dbt extracts feeding DeansList custom data objects.** Ordinary dbt work;
  `src/dbt/CLAUDE.md` governs it.
- **The DeansList UI a human drives** — running a report, configuring
  categories.

## Naming

`deanslist-report-cards`.

The earlier candidate, `deanslist-report-manager`, overpromises for a
report-cards-only skill and takes the name a general-reports skill will want.

Description, one trigger per genuinely distinct branch:

```text
Use when authoring, editing, or debugging a DeansList Report Manager report
card (ES / MS / HS progress reports) — template or partial changes, GraphQL
query changes, or diagnosing a blank or wrong render.
```

## Hard constraints

**This repo is public.** Vendor documentation, template source, and the
introspected schema stay in gitignored `.claude/scratch/`. The skill may
_describe_ the runtime and _point at_ scratch paths; it must not embed vendor
doc prose or template source. Examples in the skill are synthetic.

**PII stays local.** Student and staff names, emails, and ids appear nowhere in
the skill, in commits, or in any external write. School ids and term structure
are not PII and may appear.

## Architecture

```text
.claude/skills/deanslist-report-cards/
├── SKILL.md                          steps every branch needs
├── runtime-traps.md                  reference — reached by: diagnose
├── data-model.md                     reference — reached by: query work
├── authoring-a-report.md             reference — reached by: new report card
├── scripts/
│   ├── validate-report-queries.py    promoted from scratch, unchanged logic
│   ├── make-test-introspection.py    promoted from scratch
│   ├── check-cross-file.py           new — gate 3
│   └── splice-template.py            new — the skeleton to copy
└── example/
    ├── as-received/                  the demo's unedited source. Never edited.
    │   └── demo_report_card.{css,_head.html,.html,.js}
    ├── build/                        generated by build-demo.py. Never hand-edited.
    │   └── demo_report_card.{css,_head.html,.html,.js}
    ├── build-demo.py                 the splice: as-received -> build
    └── demo-introspection.json       synthetic schema, generated, committed
```

`SKILL.md` carries only what all four branches need. Each reference file is
reached by exactly one branch — the branching disclosure test from
`.claude/skills/writing-for-agents`, applied literally.

### Alternatives rejected

- **Split by branch** (`authoring.md`, `changing.md`, `diagnosing.md`, each
  self-contained). Every trap would land in two files — a preventive rule when
  changing, a cause when diagnosing — breaking single-source-of-truth. The brief
  also asks for a single skill, not a router.
- **Two files, maximal inline.** Traps plus authoring plus gates plus pipeline
  in one `SKILL.md` is sprawl. `fresh-dashboard/SKILL.md` is already 938 lines
  and hard to navigate; this would be worse.

## SKILL.md structure

Five steps, in order.

### Step 1 — workspace check

`.claude/scratch/deanslist/` is gitignored, so on a fresh checkout it does not
exist and every pointer in the skill dangles.

The step checks for the workspace and, if it is absent or incomplete, reports
exactly what is missing and stops. Completion criterion: the `as-received`
directory for the target template, the `build` directory, and
`schema/introspection.json` all resolve, or the step has said which do not.

The skill also names what a human must re-export to rebuild the workspace: the
four files per template, straight out of Report Manager into
`report/as-received/{template name}/`.

### Step 2 — classify the change and state the re-paste set

The most common way a correct change fails to reach production is a human
pasting three of four files. So the step's output is an explicit re-paste set,
stated before any editing begins.

| Change                      | `.css` | `_head.html` | `.html` | `.js` |
| --------------------------- | ------ | ------------ | ------- | ----- |
| Add or retire a partial     |        | yes          | yes     | yes   |
| Edit a partial's markup     |        | yes          |         |       |
| GraphQL query change        |        |              |         | yes   |
| Aggregation or hook logic   |        |              |         | yes   |
| New styling only            | yes    |              |         |       |
| New class used in a partial | yes    | yes          |         |       |
| Band gating change          |        |              | yes     | yes   |

Two rules travel with the table:

- **A partial lives in two files.** Its template is in `_head.html`; its
  `Handlebars.registerPartial(...)` call is in the `.js`. Adding a template
  without registering renders nothing, silently. Leaving a registration whose
  template was removed throws, because the lookup returns null and
  `Handlebars.compile(null)` fails.
- **MS is a band branch inside the HS template.** An MS-only change re-pastes
  the HS files.

### Step 3 — write the splice

Three directories per template, one-way:

```text
report/as-received/{template name}/   what came out of the platform. Never edited.
report/build/{template name}/         generated. Never hand-edited. The paste target.
scripts/build-chain/                  the scripts that turn one into the other.
```

Every change is a splice: a script that reads `as-received`, applies asserted
edits, and writes `build`. Nothing is hand-edited at either end. That buys three
things that matter when the only test is a human pasting into a browser:
provable blast radius (untouched regions stay byte-identical), reproducibility
(a re-run reproduces the output byte-for-byte), and recoverable state (a bad
paste is fixed by pasting `as-received` back).

The step directs the agent to copy `scripts/splice-template.py`, whose skeleton
is:

1. Locate by anchor — exact text or a verified line range, never a fuzzy
   search-and-replace.
1. Assert every anchor up front, before writing anything, so a mismatch aborts
   with nothing written. Half-applied is the worst outcome.
1. Abort with a non-zero exit on any anchor that matches a count other than
   expected. Do not warn and continue.
1. Assert post-conditions on the result: what must now be present, what must now
   be gone. Keep them specific to what the script changed — global counts of a
   shared token are brittle.
1. Print before and after line counts and the output path.

Three traps belong to splice authoring rather than to the runtime, so they live
here rather than in `runtime-traps.md`:

- **Anchor on exact bytes.** Source files carry trailing whitespace on blank
  lines, so text anchors that look right match zero times. Dump the region with
  `cat -A` first; prefer a verified line range when whitespace is unreliable.
- **A regex escape inside a Python triple-quoted string.** A backspace escape
  becomes a literal 0x08 byte in the emitted JS, producing a regex that can
  never match and that looks correct in a diff. Avoid regex escapes in generated
  code; `cat -A` exposes the byte.
- **Order matters.** Some splices read `as-received`; others patch an
  already-built file. A script in the second group must run after the one that
  generates its input, and re-running only the generator silently reverts it.
  Where a change belongs in a source file — a hand-authored partials file, or
  the generator itself — put it there so a rebuild carries it.

### Step 4 — run the gates

See [The gates](#the-gates). All four, after any change.

### Step 5 — hand off to the human

The agent's work ends at a file on disk; a human pastes it. The final report
must state which files changed and the paste order (CSS, head, body, JS), plus a
line count and a distinctive string per file so the human can confirm what
landed.

Two failure modes named explicitly, with what each looks like:

- **Pasting a subset.** A change spanning JS and head does nothing useful if
  only the JS lands, and the symptom is usually silence. The step says what a
  half-finished paste would look like on the page, so it is recognisable rather
  than mysterious.
- **Pasting a stale file.** The line count and distinctive string are the check.

## The gates

Four gates. They catch different failures and none subsumes another.

| Gate               | Command                                                                                            | Passing output                                                                                      |
| ------------------ | -------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| 1. JS syntax       | `node --check "{build dir}/{report}.js"`                                                           | no output, exit 0                                                                                   |
| 2. GraphQL         | `uv run {skill}/scripts/validate-report-queries.py {introspection.json} "{build dir}/{report}.js"` | `N/N documents validate against the schema`                                                         |
| 3. Cross-file      | `uv run {skill}/scripts/check-cross-file.py "{build dir}"`                                         | `partials: N defined / N registered / N referenced — consistent` and `classes: N used, 0 undefined` |
| 4. Reproducibility | `cp -r "{build dir}" /tmp/before`, re-run the chain, then `diff -r /tmp/before "{build dir}"`      | no output from `diff`                                                                               |

**Gate 2 re-runs after every query change.** The validator was written to catch
exactly the bug that later shipped: it was run against the baseline, three
queries were then edited, and it was never run again. `node --check` cannot see
invalid GraphQL.

**Gate 3 has a known limit worth stating in the skill.** It catches a class used
but never defined; it does not catch a class that is defined but _scoped_ so it
does not apply to your markup. That trap stays a human check in
`runtime-traps.md`.

**Gate 4 also protects the stylesheet.** The CSS is not generated by any script
— the back-page block was appended in place — so a clean rebuild loses it. The
skill says to copy the stylesheet out before any clean rebuild, wherever a
rebuild is documented.

## runtime-traps.md

Organised symptom-first, because an agent arrives holding a symptom, not a
cause. Blank-page causes are ordered cheapest-first, so the file _is_ the
diagnostic procedure and `SKILL.md`'s diagnose branch is a pointer into it
rather than a second copy of the list.

### Trap placement

Every trap in the source reference is placed. None dropped.

| Trap                                                                        | Destination                                                                    |
| --------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| Unused GraphQL variable declaration (the canonical blank page)              | traps, blank-page cause 1; the aliased-field fix also in authoring conventions |
| Partial with no registration, or registration with no template              | traps, cause 2; detected by gate 3                                             |
| Branching on an exact report key                                            | traps, cause 3; convention in authoring                                        |
| Unguarded array index in the no-try/catch stage                             | traps, cause 4; stage asymmetry in data-model                                  |
| `report.name` is not a JS path                                              | traps, wrong-values                                                            |
| `pointsBankTerms` zero-fills every term in range                            | traps, wrong-values; term interaction in data-model                            |
| Behaviour category names vary by school                                     | traps, wrong-values; catalog handling in data-model                            |
| `user.title` is empty at some schools                                       | traps, wrong-values                                                            |
| A pre-escaped entity gets escaped twice                                     | traps, wrong-values                                                            |
| Helper classes may be scoped                                                | traps, layout (gate 3 cannot see this)                                         |
| Print rules must go inside the existing print block                         | traps, layout                                                                  |
| Dictionary translation is exact-match; splitting a string creates new keys  | traps, translation; convention in authoring                                    |
| Testing a prior-year term collides with unoverridden current-year arguments | traps, testing                                                                 |
| Warehouse holds events only, no catalog                                     | data-model                                                                     |
| Schema declares no enums                                                    | data-model                                                                     |
| Term calendars                                                              | data-model, expanded to the full taxonomy                                      |
| Regex escape in generated JS                                                | SKILL.md step 3 (splice authoring, not runtime)                                |

### Deliberate drops, with reasons

Three items from `SESSION-STATE.md` are excluded on purpose:

- **A school's summer auto-award inflation.** A resolved data incident that the
  report self-corrects once the awards are deleted. Not a durable trap.
- **Repo hook blocks** on certain Bash tokens. Already documented in
  `.claude/CLAUDE.md`; duplicating it here would break single-source-of-truth.
- **Miami-specific retired partials.** Out of scope for the redesign that
  produced this material.

## data-model.md

### The five-stage pipeline

Knowing which stage a symbol appears in tells you where a failure can originate:

1. `setPreliminaryQuery` — schools, terms, behaviour categories, incident
   categories. Runs first; everything else keys off it.
1. `onPostPreliminaryStep` — derives category and term id lists, sets query
   variables, and registers a cached side request for grade-level averages.
1. `setQuery` — the main per-student query.
1. `onPreRender` — network data has landed; builds report-wide lookups and
   aggregates. **No try/catch.**
1. `onPreRenderStudent` — per-student shaping. **Wrapped in try/catch**, so an
   exception here loses one student's section, not the render.

That asymmetry is the single most useful fact in the document. An exception in
stage 4 kills everything with no error visible on the page.

### Term taxonomy

The draft material claimed "week terms run Friday to Thursday" as a flat fact.
That is a 20-of-21-schools convention, not a rule, and weeks are one of six
defined term types. Verified against `kipptaf_deanslist.stg_deanslist__terms`
for `academic_year = 2026`:

| Term type | `term_type_id` | Per school | Span            | Uniform?                                                                                 |
| --------- | -------------- | ---------- | --------------- | ---------------------------------------------------------------------------------------- |
| Weeks     | 1              | ~52        | 5–7 days        | **No** — 20 schools run Friday–Thursday (7 days); one school runs Monday–Friday (5 days) |
| Biweeks   | 7              | ~26        | 14 days         | **No** — absent entirely at 5 of 21 schools                                              |
| Months    | 6              | 12         | 28–31 days      | Yes                                                                                      |
| Quarters  | 3              | 4          | **70–125 days** | Count yes, span no                                                                       |
| Semesters | 2              | 2          | 148–216 days    | Count yes, span no                                                                       |
| Years     | 5              | 1          | **375 days**    | Yes                                                                                      |

Four consequences a report card must handle:

- **Do not hardcode a week shape.** A report card that assumes Friday–Thursday
  is quietly wrong at the one school on Monday–Friday.
- **Biweeks do not exist everywhere.** A biweek-based report card renders empty
  at 5 schools, with no error — the same silent-failure class as the trap list.
- **Year terms run 375 days**, from 1 July to roughly 10 July of the following
  year, so adjacent years overlap at the boundary. Combined with the 1 July
  start shared by the academic year, Semester 1, and Quarter 1, "year to date"
  structurally includes summer, and no term marks the actual first day of
  school. An award dated before the first week term belongs to no week at all
  and is invisible to any week-scoped aggregate.
- **Quarter spans vary from 70 to 125 days**, so a per-quarter rate is not
  comparable across schools.

The durable rule: resolve term ids by `term_type` for the student's school, and
check coverage before aggregating. Zero-filling interacts with all six types,
not just weeks.

The document records the query that produced the table so a future agent can
re-derive it for a new academic year rather than trusting a stale table.

### Catalog versus warehouse

- **The warehouse holds behaviour events only — no catalog.** 69% of live
  behaviours have never been logged, so they do not appear in BigQuery at all.
  The GraphQL schema is the only source for the catalog. A warehouse query
  returning nothing is not evidence that a behaviour or category does not exist.
- **The schema declares no enums**, so valid keyword values for arguments are
  not discoverable by introspection. They exist only in the vendor prose docs.

## authoring-a-report.md

Two parts, neither of which copies vendor prose.

**A topic index into the vendor documentation**, one line per topic naming the
page and section to read: fetching data, creating a template, helper functions,
CSS, translation, autosizing, and charts from `report-cards-101`; arbitrary
report data, additional query variables, lifecycle hooks, preliminary requests,
cached requests, and added steps from `report-cards-201`; the helper index from
`helper-functions`; schema and argument reference from `graphql-api`.

**The deltas the vendor does not document**, which is where the value is:

- The platform pins old libraries — Handlebars 2.0.0 (2014), lodash 4.17.10,
  jQuery 1.8.3, moment 2.9.0. Modern Handlebars idioms may not exist.
- The `dlrc_*` translation helpers are platform-level and not in the four files,
  so their implementation is unreadable. Treat cache-miss behaviour as unknown
  and design so a miss degrades visibly rather than silently.
- The `onPreRender` / `onPreRenderStudent` try/catch asymmetry.
- Conventions our templates chose: **add an aliased field rather than repointing
  a variable**, which keeps every declared variable in use and stops an
  unchanged label from quietly changing meaning; **derive the band from several
  sources** and log a loud, greppable blank-page cause line when none match,
  never gate on an exact report key; **join name parts in JS** rather than
  concatenating possibly-empty fields in a template; **keep an existing
  translated string verbatim** on the branch that still shows it, so only the
  new variant needs a dictionary entry.

## example/

A synthetic report card: invented fields, no real schema types, no template
source, no PII. It exists so a fresh agent has something to imitate and so the
gates are demonstrably runnable.

It mirrors the real workspace — its own `as-received` and `build` directories
with a splice between them — so the example demonstrates the pattern rather than
just describing it, and gate 4 is meaningful against it. It passes all four
gates with **nothing gitignored involved** — gate 2 validates against
`demo-introspection.json`, generated by the promoted
`make-test-introspection.py`, which builds a DeansList-shaped schema and dumps
its introspection response. The generated file is committed so the example runs
offline.

Deliberately small: one page, two partials (one of which is band-gated), one
query with two aliased fields over different term id lists, and one aggregate
that excludes zero-total terms. Between them those exercise the partial two-file
rule, the aliasing convention, the band-derivation convention, and the zero-fill
trap.

## Known gaps

Recorded in the skill rather than papered over:

- **Every trap came from editing, not authoring.** Nothing here was verified by
  building a report card from a blank slate. The synthetic example is the first
  test of that path, and it exercises the build chain, not a real render.
- **Our conventions have n=2**, and the two templates disagree: ES is
  single-band with no band gating; HS derives a band and carries the MS branch.
  Where they differ, the skill says so rather than inventing a rule.
- **Additional production examples** would strengthen the authoring reference.
  They are not a blocker; the reference is grounded in what is on disk.

## Verification

- **The criterion that matters:** dispatch a fresh subagent with only the skill
  and a small real change, and check whether it writes a splice script or
  hand-edits a build file. Writing a script is a pass. This is tested before the
  branch is considered done.
- The example's four gates run clean.
- `trunk check --force` clean on the skill's markdown, run from inside the
  worktree. Markdownlint fires at pre-push and CI, not at the pre-commit format
  hook.
- No vendor prose, template source, or PII in the diff. Checked by reading the
  diff before the PR, not asserted.
