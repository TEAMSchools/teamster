    dim_student_504_status Implementation Plan

    For agentic workers: REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (- [ ]) syntax for tracking.

    Goal: Add a 504 status SCD2 dim, roll is_504 into dim_student_enrollment_status, and expose it on the 3 student Cube views so DDI Suite and the other dashboards can slice by 504.

    Architecture: dim_student_504_status copies the Miami pm_leg shape of dim_student_ell_status: 1 span per enrollment stint where int_students__student_enrollments.is_504 is true, no source dates. The rollup left-joins it and coalesces to false. A separate Cube PR adds the dimension after the dbt PR builds in prod; a validation comparison proves it against DDI Suite's status_504.

    Tech Stack: dbt (BigQuery), Cube YAML, pytest (tests/cube/), scripts/cube_validation.

    Spec: #6284, the "For Claude" section.

    Global Constraints

    • Worktree: /workspaces/teamster/.claude/worktrees/cristinabaldor/feat/claude-504-status-dim, branch cristinabaldor/feat/claude-504-status-dim. Absolute paths and git -C on every call.
    • PR bodies say Refs #6284, never Closes: the issue outlives the dbt PR.
    • Hash keys through the macros in src/dbt/kipptaf/macros/entity_keys.sql (A7): {{ student_key("student_number") }} and {{ student_enrollment_key("student_number", "_dbt_source_project", "academic_year", "entrydate") }}. The PK has no macro: dbt_utils.generate_surrogate_key.
    • Tag every new is_504 column config.meta.contains_pii: true. Do not tag or retag other columns.
    • GitHub text carries counts only; counts under 10 read <10.
    • uv run for every dbt and pytest call. --target dev only; staging and prod writes go to the user.
    • Before each push: /workspaces/teamster/.trunk/tools/trunk check --force --no-fix <files> </dev/null from inside the worktree.

    Review Focus

    1. Two 504 stints with the same student, region, and entrydate (2 schools, 1 day) collide on student_504_status_key. The PK unique test fails the build. Prod count at plan time: 0.
    2. A zero-day stint (exitdate = entrydate) gives an end before its start. Prod count at plan time: 0. Task 1 step 4 checks it.
    3. Miami's unset (null) is_504 must read false in the rollup, not null. Task 2 step 3 checks it.
    4. Graduate placeholders (null entrydate) must not reach the dim. The where filter does this; Task 1 step 4 counts it.
    5. A Cube query sliced by is_504 cannot use the proficiency_rollup pre-aggregation, which does not carry is_504, so it reads the raw fact. Task 4 step 5 records the dry_run result. Adding is_504 to the rollup is out of scope.

    • Step 2: Write dim_student_504_status.sql

    1 CTE reads int_students__student_enrollments:

    • where is_504 and entrydate is not null (is_504 is null in Miami when unset; where is_504 drops null and false alike).
    • entrydate as effective_date_start.
    • coalesce(date_sub(exitdate, interval 1 day), cast('9999-12-31' as date)) as effective_date_end with the ELL dim's half-open comment.

    The final select matches the ELL dim's order and shapes, using the macros from Global Constraints for student_key and student_enrollment_key, and true as is_504.

    • Step 3: Write the properties YAML

    Copy properties/dim_student_ell_status.yml and change:

    • Model description: SCD2 504 plan status per student per district. 1 span per enrollment stint whose 504 flag is set; no source carries 504 begin or end dates, so each span covers the whole stint. Inclusion-based: consumers default to false when no row covers the date. NJ past stints carry a per-stint value; the current NJ stint and every Miami stint carry the student's current value. Keep it source-agnostic: field names go in config.meta.source_column, not the description.
    • Tests: unique on student_504_status_key, not_null on _dbt_source_project. No other column tests: the SQL guarantees is_504, is_current, and both date keys are non-null (.claude/rules/dbt-yaml.md, Choosing a test).
    • is_504 gets config.meta.contains_pii: true and a description saying it is true on every row.
    • Date-key descriptions: start is the stint's entry date; end is the day before exit, 9999-12-31 while the stint is open.

    • Keep the config.meta.foreign_key blocks and the dagster meta with asset_key: [kipptaf, marts, dim_student_504_status].

    Task 2: Roll is_504 into dim_student_enrollment_status

    Files:

    • Modify: src/dbt/kipptaf/models/marts/dimensions/dim_student_enrollment_status.sql
    • Modify: src/dbt/kipptaf/models/marts/dimensions/properties/dim_student_enrollment_status.yml

    Interfaces:

    • Consumes: dim_student_504_status.student_enrollment_key, .is_504 (Task 1).

    • Produces: dim_student_enrollment_status.is_504 (boolean, never null). Task 4 twins its description.

    • Step 1: Edit the SQL

    Add a CTE section_504 after ell, with the comment -- 504: at most one span per stint; LEFT JOIN returns NULL when absent., selecting student_enrollment_key, is_504 from dim_student_504_status. Left-join it, aliased s5, to enr on student_enrollment_key, and add coalesce(s5.is_504, false) as is_504 after is_ell in the boolean block.

    • Step 2: Edit the YAML

    Add is_504 after is_ell, with data_type: boolean, config.meta.contains_pii: true, and this description, verbatim (Task 4 copies it):

    TRUE if the student had a Section 504 plan during this enrollment stint.
FALSE when no 504 record covers the stint, including when the source system
leaves the flag unset, as it does for most Miami students and every
current-year Paterson student. This is the enrollment 504 status the
assessment dashboards show; state test files carry their own 504 flag, which
can differ.

    Add 504 to the model description's list of rolled-up statuses ("ELL, IEP, 504, and meal eligibility"; "504 via LEFT JOIN (one span per stint)").

    with expected as (
    select
        to_hex(md5(concat(
