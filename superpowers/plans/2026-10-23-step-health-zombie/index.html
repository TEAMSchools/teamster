    Fail Fast on Zombie Step Jobs Implementation Plan

    For agentic workers: REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (- [ ]) syntax for tracking.

    Goal: A step whose Kubernetes Job completed more than 60 s ago, while the run pod still treats the step as running, is reported unhealthy so the step fails and the run's auto-retry takes over.

    Architecture: A K8sStepHandler subclass adds one rule after upstream's check_step_health. An executor definition wraps k8s_job_executor: it builds the stock StepDelegatingExecutor and swaps its handler's class for the subclass. All 5 code locations use the wrapper.

    Tech Stack: Python 3.13, dagster, dagster-k8s 0.29.26, kubernetes client models, pytest.

    Spec: docs/superpowers/specs/2026-10-23-step-health-zombie-design.md

    Global Constraints

    • Grace period: 60 s, one module constant.
    • No upstream init code copied from dagster_k8s/executor.py.
    • The wrapper keeps k8s_job_executor's name ("k8s"), config schema, and requirements unchanged.
    • Upstream's unhealthy results (Job missing, Job failed) pass through unchanged.
    • Unhealthy reason contains the stable substring completed without a step result (the day-2 classifier matches it).
    • Run tests with uv run pytest tests/test_dagster_executors.py only; never bare uv run pytest.

    Review Focus

    • Job status with succeeded set but completion_time None → healthy (no crash). Test in Task 1.
    • completion_time is timezone-aware UTC from the k8s client; compare against an aware datetime.now(UTC), never naive. Test in Task 1 uses aware values.
    • Upstream raises from get_job_status (API error) → exception propagates unchanged; StepDelegatingExecutor already catches and logs it. Test in Task 1.
    • The wrapped executor exposes the same config schema as the stock one, so existing executor run config still validates. Test in Task 2.
    • The swap must reach the handler the executor actually calls (_step_handler); a dagster-k8s upgrade that renames it must fail a test, not silently skip the fix. Test in Task 2.

    • Step 3: Implement ZombieAwareK8sStepHandler in src/teamster/core/executors.py

    check_step_health returns super().check_step_health(...) when that result is unhealthy. Otherwise it re-reads the Job status through self._api_client.get_job_status(namespace=..., job_name=...) (same calls upstream uses) and returns CheckStepHealthResult.unhealthy(...) when status.succeeded and status.completion_time is more than ZOMBIE_JOB_GRACE_SECONDS before datetime.now(UTC). Reason text: f"Kubernetes job {job_name} for step {step_key} completed without a step result {age}s ago. Its replacement pod likely exited on Dagster's duplicate-start guard." Comment on the constant: one line saying it sits far above the run pod's lag in reading a step's success event, so a healthy step never trips it (Refs #6103). Class docstring (Google style) says what the extra rule catches; put the upstream link dagster-io/dagster#33755 in the extended description.

    • Step 4: Run tests to verify they pass

    Run: uv run pytest tests/test_dagster_executors.py -v 2>&1 | tail -n 30 Expected: 7 passed.

    • Step 3: Implement zombie_aware_k8s_job_executor

    An @executor(name="k8s", config_schema=k8s_job_executor.config_schema, requirements=multiple_process_executor_requirements()) function that calls k8s_job_executor.executor_creation_fn(init_context), checks the result with check.inst(executor, StepDelegatingExecutor) and check.inst(executor._step_handler, K8sStepHandler), then sets executor._step_handler.__class__ = ZombieAwareK8sStepHandler and returns it.
