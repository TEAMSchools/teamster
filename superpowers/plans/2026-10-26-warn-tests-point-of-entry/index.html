    Warn Tests at Point of Entry Implementation Plan

    For agentic workers: REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (- [ ]) syntax for tracking.

    Goal: Move the source-data warn tests listed in #6146 to the earliest model that sees the bad rows, and delete their downstream copies in the same PR.

    Architecture: dbt test and YAML changes only, across 4 dbt projects (powerschool, focus, finalsite, kipptaf). One commit per project; kipptaf gets two (enrollment and contacts; assessments). No model SQL changes except comments (item 12, item 13).

    Tech Stack: dbt on BigQuery, dbt_utils, dagster-dbt checks.

    Spec: docs/superpowers/specs/2026-10-26-warn-tests-point-of-entry-design.md. Read it first; this plan does not repeat its reasoning.

    Global Constraints

    • Every new or moved test is severity: warn. Package tests set it explicitly; packages default to error.
    • Every singular package test gets a tests/properties.yml entry with meta.dagster.ref.name (a model the test reads) and package: <source>. kipptaf entries omit package:.
    • Every singular kipptaf test that reads more than 1 model gets meta.dagster.ref.
    • Descriptions name the source system, what is wrong, and what to change there. No issue numbers in descriptions; TODO(#N) and Refs stay in SQL comments.
    • Ticket columns: record, period, school. Network-level records (Illuminate assessment, repository field) return record id, title, academic year, and creator_* where available, no school.
    • No row values in commits, PR text, or comments. Counts only.
    • Run uv run for every dbt call. Use absolute worktree paths, never cd to the main checkout.
    • --target prod is allowed only for dbt compile and dbt parse (they write nothing). Never dbt build/run/test --target prod or --target staging.

    How to check a test's count (used by every task)

    dbt has no read-only way to run a test against prod, so compile it and run the compiled SQL through the BigQuery MCP.

    1. uv run dbt deps --project-dir <wt>/src/dbt/<project> once per project.
    2. uv run dbt compile --select <test_name> --project-dir <wt>/src/dbt/<project> --target prod 2>&1 | tail -n 5
    3. Read the compiled file under <wt>/src/dbt/<project>/target/compiled/ and run select count(*) from (<compiled sql>) with mcp__claude_ai_Google_Cloud_BigQuery__execute_sql_readonly (project teamster-332318).
    4. Compare with the expected count. A difference over about 10% gets explained (data moved since 2026-10-26 is a valid explanation) before you commit.

    For a package test, compile in each consuming district: powerschool → kippnewark, kippcamden, kipppaterson; focus → kippmiami; finalsite → all 4.

    <wt> = /workspaces/teamster/.claude/worktrees/cbini/fix/claude-warn-tests-point-of-entry.

    Review Focus

    1. A package test in a district with no data for it (finalsite tests in kippmiami; powerschool tests in kipppaterson) should return 0 or real rows, not fail to compile. Task 3 counts kippmiami separately.
    2. int_powerschool__ps_enrollment_all.yearid is null when entrydate falls outside every term. The skipped-grade test derives the year from entrydate, so those stints are not dropped. Task 1 checks that the null-yearid count is unchanged by the derivation.
    3. academic_year_clean of 0 or 1 makes date() throw. The item 9 test filters academic_year_clean >= 2000 before calling date(). Task 5 compiles and runs it over all history to prove no error.
    4. A singular package test without package: silently never becomes a Dagster check. Task 6 checks every new entry in the parsed manifest.
    5. Repositories with no int_illuminate__repositories row must not fail item 10's test. An inner join excludes them; Task 5 checks the count is 6, not 14.

    • Step 1: Write int_powerschool__ps_enrollment_all__no_skipped_grade.sql

    Logic: from ref("int_powerschool__ps_enrollment_all"), exclude schoolid = 999999 and grades outside 0–12. Derive academic_year from entrydate (July starts the year: extract(year from entrydate) minus 1 when the month is before 7). Take 1 row per studentid, academic_year with the highest grade_level and that row's schoolid (rank by grade_level desc, entrydate desc). In a second CTE, compute lag(academic_year) and lag(grade_level) over partition by studentid order by academic_year. Return rows where academic_year - prior_academic_year = 1, grade_level - prior_grade_level > 1, and grade_level between 9 and 12. Output columns: studentid, student_number, academic_year, schoolid, prior_grade_level, grade_level. Follow .claude/rules/dbt-sql.md: ranked column plus where, no qualify.

    • Step 2: Check its count

    Use How to check a test's count. Expected: Newark plus Camden total 117, Paterson 0. Current-year rows: 7.

    • Step 3: Write int_powerschool__spenrollments__no_concurrent_bucket_per_subject.sql

    From ref("int_powerschool__spenrollments") where specprog_name like 'Bucket%', derive subject as the text after the hyphen (trimmed). Self-join on studentid, academic_year, subject, with a.specprog_name < b.specprog_name and overlapping ranges (a.enter_date < b.exit_date and b.enter_date < a.exit_date, treating a null exit as open). Return studentid, academic_year, subject, both program names, both enter dates. For the school, join whatever upstream model holds the student's schoolid. Read int_powerschool__spenrollments.sql first; if stg_powerschool__spenrollments carries schoolid, join that on dcid.

    • Step 4: Check its count

    Expected: 54 pairs, all AY2025 (Camden 29, Newark 20, Paterson 5). If the overlap condition drops any pair, check the 1 inverted-date Newark record #5693 mentions (exit before enter). Treat an inverted range as overlapping when the enter dates match.
