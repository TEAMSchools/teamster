    Module Dashboard Completion and Pivot Implementation Plan

    For agentic workers: REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (- [ ]) syntax for tracking.

    Goal: Deliver a review copy of the DDI Suite whose Module Dashboard shows an accurate completion %, hides cells under 75% complete, and lets a user pivot the 2 main heatmaps by grade level or high school course subject.

    Architecture: Every change is an edit to the workbook's .twb XML, made by re-runnable Python scripts against a fresh download of the review copy. The extract already holds the not-taken rows, so no dbt model changes. An independent SQL oracle over the packaged .hyper proves the completion numbers.

    Tech Stack: Tableau .twb XML, Python (tableauserverclient, tableauhyperapi through uv run --with), the scripts in docs/tableau-xml/scripts/, pytest as the credential runner.

    Spec: docs/superpowers/specs/2026-11-23-module-dashboard-completion-pivot-design.md. Read it first. The formulas, the cell grain and the list of sheets live there and are not repeated here.

    Global Constraints

    • Invoke the tableau-workbook-xml skill before any workbook work and follow its loop. Invoke ddi-stack for dashboard terms. Where this plan and the skill disagree on mechanics, the skill wins.
    • Base workbook: luid 652f1c0a-371a-42ee-807a-61a3915e3af2 (ZZ-REVIEW 2026-11-12 DDI Suite goal columns). Never publish over it.
    • Never publish to the Production project. The production DDI Suite is luid 6d82b643-59a8-4106-b2f9-97ddf7f638e7; no step here touches it.
    • Every copy is published to GPA-monitor-temp, c74d8e08-b856-4430-a759-ebacb061e376, the project the user named. No other project id appears in a publish call.
    • Every published name starts ZZ-REVIEW <YYYY-MM-DD> DDI Suite module completion. Probe copies append PROBE <variant>.
    • No dbt, Cube or Dagster file changes. If a step seems to need one, stop and ask the user.
    • Worktree: /workspaces/teamster/.claude/worktrees/anthonygwalters/feat/claude-module-dashboard-completion-pivot (called <wt> below). Reach it by absolute path and git -C <wt>.
    • Scripts and workbook files live in <wt>/.claude/scratch/tableau/, which is gitignored. Only the docs change in Task 7 is committed.
    • Student-level rows (the .hyper, exported CSVs) stay in scratch. Nothing student-level goes to git, GitHub or the final report. Report aggregates only.
    • Read every .twb with encoding="utf-8", newline="" and write it the same way. The file uses CRLF line endings.
    • Every substitution asserts how many times it matched. A calculated field's <column> element is repeated: once in the datasource and once in the <datasource-dependencies> of every worksheet that reads it. An edit to a formula changes every copy, and the assertion counts them.
    • Read exit codes with a redirect, never through a pipe.
    • Avoid Tableau MCP calls while a publish or export is running. They share the token and can end the session.

    Review Focus

    1. A worksheet that reads % Completion but lacks a dependency declaration for Heatmap Column or the new parameter. Server may render it and Desktop may refuse it. Pinned by the dependency assertion in Task 4.
    2. A mark that mixes a due assessment with one not yet due. Its mastery value legitimately changes, because early scores for the not-yet-due assessment are now hidden. Pinned by the exclusion list in Task 6, check A.
    3. A cell with no counted assignment (possible is 0). Completion must be null and the cell hidden, not an error or 100%. Pinned by the oracle comparison in Task 6, check B.
    4. Grade order on the heatmap columns. A string sort puts 10 before 2. Pinned by the column-order check in Task 6, check D.
    5. The shared response_type filter (group 27) losing its context flag on only some of its sheets. Pinned by the count assertion in Task 2.

    File Structure

    All under <wt>/.claude/scratch/tableau/:

    Path Responsibility
    server/base.twbx Fresh download of the base, with its extract
    server/base.twb The untouched XML. --ref and --baseline for every check
    module-dashboard/build.py Applies every edit in order. The one entry point
    module-dashboard/asserts.py One assertion function per task, runnable by name
    module-dashboard/oracle.py Computes cell completion from the .hyper
    module-dashboard/compare.py Compares exported sheet data with the oracle and with the base
    module-dashboard/out/ Built .twb and .twbx files

    Credentialed steps run from a throwaway <wt>/tests/test_zz_module_dashboard.py, copied from docs/tableau-xml/scripts/tsc_session.py and run with cd <wt> && uv run pytest tests/test_zz_module_dashboard.py -s. Delete it in Task 7.

    """Return the edited .twb text. Each edit_* runs once, in task order."""

    Columns: academic_year, schoolid, subject_area, module_type,
    module_number, is_replacement, heatmap_column, grade_levels (set),

    Expected: base.twbx over 20 MB; base.twb about 3 MB with CRLF endings.

    • Step 2: Check the base has not drifted. Confirm these facts, which the spec depends on. If any fails, stop and report: the design was made against a different file.

    • [% Completion (copy)] formula contains SUM([Calculation_860187586860363778]).

    • Module - Overall - Network Overview and Module - Overall - Assessments Over Time have [none:grade_level:ok] in <cols>.

uv run python docs/tableau-xml/scripts/check_geometry.py <base.twb> "Module Dashboard" --baseline <base.twb> >/tmp/o2 2>&1; rc2=$?

    Expected: both exit 0. A failure here is a checker problem; report it before editing anything.

    • Step 4: Confirm the extract holds not-taken rows. Unpack the rpt_tableau__assessment_dashboard .hyper from base.twbx (its dbname is on the datasource's <extract><connection>). With uv run --with tableauhyperapi --with pandas, count rows in "Extract"."Extract" where response_type is null and academic_year is 2026, by region.

    Expected: tens of thousands for Newark and Camden, thousands for Paterson, none for Miami. If the count is 0, stop: the workbook has a datasource or extract filter the spec did not account for.

    • Step 5: Write oracle.py. It implements the spec's Definitions section in SQL over the .hyper, independently of the workbook's formulas. heatmap_column follows the spec's Heatmap Column formula. n_scored_rows counts overall rows with a non-null percent_correct (the rows a sheet can show). has_not_yet_due is true when the cell holds any row with administered_at after today.

    • Step 6: Sanity-check the oracle. Pooled n_complete / n_possible by region for 2026, pivot="Grade Level".

    Expected: Camden, Newark and Paterson between 60% and 85%; Miami at or near 100%. (Prod measured 69%, 73%, 75% on 2026-11-23; the extract is older, so expect nearby values, not equal ones.)

    Task 2: Completion calcs and the context filter

    • Consumes: base.twb.

    • Produces: edit_completion(text: str) -> str; the 3 completion calcs with the spec's formulas, using [grade_level] where the spec writes [Heatmap Column]. Task 4 swaps that one token.

    • Step 1: Write the completion assertion. It passes only when all of these hold:

    • No <calculation> formula contains SUM([Calculation_860187586860363778]).

    • Every copy of [Student Baseline Count (copy)] and [Calculation_860187586860363778] has a formula containing [administered_at] <= TODAY() and STR([student_number]), and none contains [is_pathways].
    • Every copy of [Student Baseline Count (copy)] contains ISNULL([response_type]).
    • The number of copies of each of the 3 calcs equals its count in base.twb.
    • The 17 worksheets the spec lists have a [none:response_type:nk] filter without context='true'; its <groupfilter> members are unchanged from the base; filter-group='27' is still on the same 15.

    • Every other context='true' in the file is unchanged from the base (compare counts per worksheet).

    • Step 2: Run it on the base.

    Run: uv run python asserts.py <base.twb> completion; echo $? Expected: exit 1, naming the first failed condition.

    • Step 3: Implement edit_completion. Formulas come from the spec. Inside an XML attribute, a line break is &#10;, an apostrophe is &apos;, < is &lt;. Keep each calc's caption, datatype, role and default-format.

    • Step 4: Build and assert.

    Run: uv run python build.py <base.twb> out/out.twb then uv run python asserts.py out/out.twb completion; echo $? Expected: exit 0. ET.fromstring parses the output.

    • Step 5: Prove the assertion bites. Hand-write 2 broken variants of out.twb and confirm each fails: one copy of % Completion left with the old formula; one of the 17 sheets left with context='true'.

    • Step 6: Run both checkers against out.twb with --ref and --baseline set to base.twb.

    Expected: both exit 0.

    • No formula of the 3 completion calcs or the pooled calc contains [grade_level]; each contains [Heatmap Column].
    • Dependency rule: every worksheet whose <datasource-dependencies> declares [% Completion (copy)] also declares [Heatmap Column], and declares [Heatmap Columns] under a Parameters dependency block.

    • Step 2: Run it on the Task 3 output. Expected: exit 1.

    • Step 3: Implement edit_pivot. Model the parameter on [Group By (copy)] (caption Dashboard View), a 2-member string list.
